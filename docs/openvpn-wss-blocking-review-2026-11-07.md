# Проверка гипотез о блокировках OpenVPN WSS — 7 ноября 2026

По дампу и доступному коду нельзя установить, что ТСПУ распознаёт именно OpenVPN
внутри WSS. Есть реальные отказы доступности с российской точки проверки, но
прежний разбор смешивает наблюдения, гипотезы и слишком сильные выводы.

Проверены локальный дамп `datagate_db_prod_backup_20261107_100638.dump`, код
backend/OpenVPN/Xray/installer и публичные HTTPS-интерфейсы перечисленных серверов.
Конфигурация действующих хостов через SSH, клиентские приложения, firewall и
захваты пакетов не исследовались. Производственные настройки не менялись.

TimescaleDB. Использовался последовательный вариант.

Это существенно сильнее прежнего совпадения внешних мобильных IP за ±2 часа.

В `backend/DataGateMonitor/Services/Helpers/VpnSessionIdGenerator.cs` ключ сессии
включает `CommonName`, адрес и время начала. Парсер статуса в

`CommonName=UNDEF`. Смена имени меняет ключ; синхронизация в
`Services/BackgroundServices/VpnServerService.cs` обрабатывает его как другую
сессию. Данные совместимы с переходом между неидентифицированным и именованным
состоянием; направление каждого перехода отдельно не восстановлено.

Например, у 160 запись UNDEF от `2026-11-07 04:46:54 UTC` содержит 261 160 445 байт,
а именованная запись с тем же сокетом и временем — 261 159 723 байта. Считать обе
записи независимыми попытками или просто суммировать их трафик некорректно.

Остальные 9 записей этим сопоставлением не идентифицированы. Они могут включать
неуспешные клиентские подключения; считать их доказанно зондами или доказанно
обычными клиентами нельзя. Один мобильный публичный IP также может обслуживать
многих абонентов через CGNAT. Причинной связи UNDEF с блокировкой не установлено.
UNDEF не является счётчиком всех активных проб: HTTP/TLS-проба может вообще не
попасть в таблицу OpenVPN-клиентов.

## Что действительно видно из конфигурации

1. Для OpenVPN наружный TLS завершает nginx, затем WebSocket проксируется в
   менеджер, который соединяется с OpenVPN на loopback.
2. Для основного прямого Xray TLS-inbound nginx `stream` использует
   `ssl_preread` и передаёт соединение самому Xray. Это разные реализации TLS.
   См. `install/vpns/templates/nginx-docker/nginx/stream.d/sni-xray.conf` и
   `xray/scripts/xray/render-config.sh`. API на 9443 и возможный WSS-путь Xray —
   другие интерфейсы. Фактический путь каждой клиентской сессии нужно проверять
   отдельно. У рассматриваемых Xray-сессий в базе публичные peers и пустой
   ProxyRealIp, что совместимо с прямым путём.
3. Совпадение сертификатов одного удостоверяющего центра не делает одинаковыми
   TLS-отпечатки клиента, сервера и поведение соединения. Нельзя исключить nginx
   или клиентский ClientHello только потому, что живёт Xray.
4. В шаблонах nginx не задан `ssl_protocols`; современные версии используют
   TLS 1.2/1.3 по [документации nginx](https://nginx.org/en/docs/http/ngx_http_ssl_module.html#ssl_protocols).
   Настройки nginx не заменяют ClientHello, создаваемый приложением клиента.
5. TLS скрывает содержимое WSS, включая URL и WS-фреймы, от обычного пассивного
   наблюдателя. Размеры, направления и интервалы передачи могут сохранять
   различимые признаки: это прямо описано в [RFC 8446, E.3](https://www.rfc-editor.org/rfc/rfc8446.html#appendix-E.3).
   Возможность анализа зашифрованного трафика не доказывает распознавание данной
   реализации и не позволяет назвать её «основным способом блокировки в РФ».
6. В наблюдаемых записях 160–163 нет non-loopback peers. Это подтверждает путь
   учтённых сессий, но не доказывает отсутствие открытого слушающего порта или
   всех неуспешных сканирований. Сам installer предусматривает loopback binding.
7. Публичный `/api/proxy` даёт узнаваемый ответ. Такой же ответ есть и у живого
   Xray API, и у старого OpenVPN. Его наличие само по себе не объясняет различие
   исходов. Скрытие URL не меняет видимый пассивному DPI ClientHello.

Дополнительно: пересечение пользователей между живыми и недоступными узлами не
исключает получение адресов через учётную запись. Доступность соседнего адреса
в /24 также не изолирует протокол от истории IP, DNS-имени, клиентского стека,
оператора или порта.

## Следующие действия, которые различат гипотезы

1. Проверить новые подключения на существующие адреса из двух-трёх независимых
   сетей РФ, одновременно с контрольной сетью вне РФ. Разделить результаты DNS,
   TCP connect, TLS handshake, HTTP и авторизации VPN. Сохранять время, адрес
   назначения, SNI, порт и точку проверки. Один `reachable` для API не заменяет
   проверку пользовательского туннеля.
2. Во время одной известной контрольной попытки посмотреть на сервере SYN,
   SYN-ACK и TLS handshake, а также firewall/Wazuh/Fail2ban, если установлены.
   Захват ограничить адресом тестового клиента. Это покажет, приходит ли запрос
   и уходит ли ответ, не затрагивая трафик остальных пользователей.
3. Сопоставить ClientHello реального OpenVPN WSS-клиента и реального Xray-клиента.
   Проверить отсутствие обходного прямого подключения и проверку сертификата в
   приложениях. Код приложений в этой проверке отсутствовал.
4. Исправить переход UNDEF ↔ имя в учёте сессий: сохранять стабильную идентичность
   соединения либо явно объединять состояния. Не удалять исторические записи и
   не менять общий генератор ID без проверки событий connect/disconnect,
   накопительных счётчиков, квот и отличий Xray.
5. Эксперимент с отдельными IP для UDP-over-WSS и TCP-over-WSS полезен только после
   таких измерений. По возможности уравнять возраст/провайдера адресов, порт,
   клиентскую версию, аудиторию, TLS-политику и интенсивность. Оба варианта снаружи
   идут по TCP/TLS. Один исход на каждой из двух машин не докажет TCP-in-TCP,
   необходимость сочетания протоколов или универсальную распознаваемость OpenVPN.

Смена шифров nginx, случайный URL, статическая заглушка, Xray или Reality сами
по себе не дают гарантии от блокировки. Приоритет Xray может быть практической
мерой для текущей доступности, но из этого дампа нельзя вывести неизбежность
блокировки каждого OpenVPN WSS или надёжность определённого тарифного ограничения.

## Дополнение: присланный разбор Android-клиента

После первичной проверки пользователь передал описание Kotlin-мостов и
клиентского Xray. Самих `TcpToWssBridge.kt`, `UdpToWssBridge.kt`,
`XrayConfigBuilder.kt` и остальных упомянутых Kotlin-файлов среди доступных
проектов не найдено. Их реализация и версия Xray-core внутри libXray независимо
не проверены. Описание полезно как дополнительная гипотеза о пути трафика,
с приведёнными ниже уточнениями.

- **TCP read, WS-сообщение, TLS-запись и TCP-сегмент — разные границы.**
  TCP `read()` может вернуть часть одного или данные нескольких сообщений
  OpenVPN. Даже при одном WS-сообщении на каждый read TLS может дробить и
  объединять данные; на проводе также добавляются служебные поля WebSocket.
  [RFC 8446, §5.1](https://www.rfc-editor.org/rfc/rfc8446.html#section-5.1)
  допускает дробление и объединение application data между TLS-записями.
  Нельзя вывести отображение размеров «один к одному» без измерения конкретных
  OkHttp/Conscrypt. Это не исключает статистической корреляции размеров/времени.
- **UDP сохраняет границы датаграмм в прикладном framing, но не обязательно
  в наружных пакетах.** В текущем серверном `OpenVpnProxyController.cs`
  `PumpUdpToWebSocket()` группирует уже ожидающие датаграммы в пачки, поэтому
  утверждение «одна датаграмма — одно WS-сообщение» не описывает оба направления.
  Текстовый JSON connect-кадр текущий `PumpWebSocketToUdp()` пропускает, обрабатывая
  только binary-сообщения; за внешним TLS его содержимое пассивно не видно.
- **Chrome по умолчанию подтверждён для локального core.** В
  `xray/xray/transport/internet/tls/tls.go:239`, commit `1b1647cd`,
  `GetFingerprint("")` возвращает `utls.HelloChrome_Auto`.
  XHTTP dialer использует этот результат при создании TLS-клиента.
  [Актуальная документация Xray](https://xtls.github.io/en/config/transports/tls.html#tlsobject)
  также указывает Chrome по умолчанию и отдельно предупреждает: имитация
  ClientHello не превращает остальное поведение в браузерное. Для Android нужно
  сверить версию встроенного core и итоговый JSON-конфиг. Явный `fp=chrome`
  фиксирует намерение, но не является доказанным исправлением блокировок.
- **XHTTP не гарантирует отсутствие характерных следов.** Локальная реализация
  поддерживает `packet-up`, `stream-up` и `stream-one`; потоковые HTTP-запросы
  могут быть длительными. `XPadding` по умолчанию имеет диапазон 100–1000,
  а код применяет его в том числе к заголовкам, query и cookies запросов/ответов.
  Из этого не следует случайный padding каждого блока передаваемых данных или
  полное исчезновение их размеров и ритма.
- **У XHTTP есть собственное управление соединениями.** `getHTTPClient()`
  создаёт `XmuxManager`, даже если transport `xmux` не задан явно. Это отдельный
  механизм от верхнеуровневого Xray `mux`. Для HTTP/2 текущий dialer по умолчанию
  задаёт `ReadIdleTimeout=45s`: проверка соединения зависит от отсутствия
  входящих данных. Противопоставление «строго периодичный WS — непериодичный h2»
  нельзя принять без захвата трафика.
- **Разница портов остаётся смешивающим фактором.** OpenVPN WSS на 443 и XHTTP
  на 2053 одновременно различаются транспортом, портом, доменом и клиентским
  TLS-стеком. Успех одного варианта не выделяет в качестве причины именно
  вложенное TLS-рукопожатие OpenVPN. У VLESS также есть собственные служебные
  заголовки, хотя отдельного TLS control channel OpenVPN у него нет.

Новые сведения поддерживают проверку гипотезы о статистическом распознавании
моста без специального маскирования. Они пока не устанавливают конкретный
детектор ТСПУ и не обосновывают утверждение «XHTTP таких следов не оставляет».
